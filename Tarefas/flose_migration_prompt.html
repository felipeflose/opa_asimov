// 01 — DIAGNÓSTICO

Problemas Críticos
do Sistema Atual

Após análise completa do codebase (entrypoint.py, App.jsx, orquestrador, agentes, storage e CI/CD), foram identificados os seguintes anti-padrões críticos que tornam o sistema frágil, difícil de manter e caro de operar:

⚠ Problema #1 — God Files

O entrypoint.py tem mais de 700 linhas com 40+ endpoints, lógica de negócio, autenticação, manipulação de GCS, orquestração de agentes e servir arquivos estáticos — tudo misturado. O App.jsx tem 2.500+ linhas com UI, estado global, lógica de negócio e chamadas de API sem separação.

⚠ Problema #2 — Nenhuma Separação de Responsabilidades

Não existe separação entre camadas (UI → BFF → Serviços → Storage). A autenticação é feita de 3 formas diferentes. O estado é gerenciado de forma ad-hoc com useState local, sessionStorage, localStorage e estado Streamlit simultâneos.

⚠ Problema #3 — Orquestrador Sobrecarregado

O CognitiveOrchestrator faz: sanitização, embedding, busca vetorial, memória episódica, memória compartilhada, DORA metrics, knowledge graph, afinidade de agentes, FinOps, retry de API e lógica de decisão — tudo em um único método process_command(). É impossível testar ou debugar isoladamente.

⚠ Problema #4 — Frontend Monolítico sem Estado Gerenciado

O App.jsx tem 50+ useState hooks no escopo raiz. Sem Context, Redux ou Zustand. Cada tab recarrega dados completos. O handleOrchestratorCommand é referenciado mas nunca definido — o código já está quebrado.

⚠ Problema #5 — Segurança Frágil

Token passado via query param como fallback (?token=...). O API_TOKEN é definido no escopo global do processo. O validate_token() aceita token nulo se MASTER_KEY não estiver configurada. A página Streamlit salva credenciais em .env local via subprocess.

⚠ Problema #6 — Zero Testes

Apenas 2 arquivos de teste (test_gcs.py e test_finops.py) com cobertura mínima. Nenhum teste de integração, nenhum teste de endpoints da API, nenhum teste dos agentes.

⚠ Problema #7 — Duplicação e Inconsistência

Dois sistemas de dashboard paralelos: Streamlit (src/dashboard/) e React (frontend/). Dois sistemas de autenticação. Dois sistemas de log. O grafo de conhecimento tem nós "lixo" filtrados em runtime em vez de na inserção.

Refatoração do Backend
Python / FastAPI

Você é um arquiteto de software sênior especializando em Python e FastAPI. Vou te dar o código atual de um sistema monolítico e você vai refatorá-lo seguindo Clean Architecture e o padrão BFF.

Exemplo: auth.py correto

# api/auth.py — JWT única, sem fallbacks
from datetime import datetime, timedelta
from jose import JWTError, jwt
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

SECRET_KEY = os.environ["MASTER_KEY"]  # Falha explicitamente se ausente
ALGORITHM = "HS256"
security = HTTPBearer()

def create_token(admin_id: str) -> str:
    expire = datetime.utcnow() + timedelta(hours=8)
    return jwt.encode(
        {"sub": admin_id, "exp": expire},
        SECRET_KEY, algorithm=ALGORITHM
    )

async def require_auth(
    credentials: HTTPAuthorizationCredentials = Security(security)
) -> str:
    try:
        payload = jwt.decode(credentials.credentials, SECRET_KEY, algorithms=[ALGORITHM])
        return payload["sub"]
    except JWTError:
        raise HTTPException(status_code=401, detail="Token inválido")
// 04 — PROMPT: BFF

Construção da
Camada BFF

CONTEXTO: Estou construindo a camada BFF (Backend For Frontend) de uma plataforma de IA. O frontend é React + Vite. O backend core é Python/FastAPI.

O BFF precisa:

1. Agregar dados de múltiplas sources em uma única chamada — ex: /api/dashboard retorna stats + agentes + tasks recentes em uma query

2. Transformar os dados do backend para o formato exato que o React precisa — sem lógica de transformação no frontend

3. Cachear respostas pesadas em memória por 30 segundos (stats, grafo de conhecimento)

4. SSE (Server-Sent Events) para o feed de atividades em tempo real — em vez de polling a cada 5s

5. Validação de schema com Pydantic antes de retornar ao frontend

Implemente o endpoint /api/dashboard que agrega:

— Stats do FinOps (tokens, custo, chamadas do dia)

— Contagem de agentes ativos

— Tasks por status (aberto, em progresso, concluído)

— Últimas 5 atividades

— Score de saúde do sistema (0-100)

E o endpoint SSE /api/activity/stream que envia eventos a cada 10s com novas atividades.

Use asyncio para paralelizar as queries. Use functools.lru_cache com TTL para o cache. Documente cada endpoint com OpenAPI summary e description.

Exemplo de Hook React Query

// api/hooks/useAgents.js
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query'
import { apiClient } from '../client'

export function useAgents() {
  return useQuery({
    queryKey: ['agents'],
    queryFn: () => apiClient.get('/api/agents').then(r => r.data),
    staleTime: 60_000,
  })
}

export function useUpdateAgent() {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: ({ id, data }) => apiClient.patch(`/api/agents/${id}`, data),
    onSuccess: () => qc.invalidateQueries(['agents']),
  })
}

Simplificação do
Orquestrador Cognitivo

O orquestrador atual tem 15+ responsabilidades misturadas. Preciso decomposição radical.

ATUAL (problemático): Um método process_command() com 200+ linhas que faz: sanitização de input, busca vetorial, memória episódica, memória compartilhada, histórico de chat, chamada Gemini, validação Pydantic, roteamento de ação, execução de agente, tracking de afinidade, log no BigQuery, update do knowledge graph, e episódio na memória.

ALVO (limpo): Separe em classes distintas com injeção de dependência:

InputProcessor — sanitiza e prepara o contexto (máx 50 linhas)

ContextBuilder — monta contexto de memória + histórico (máx 80 linhas)

GeminiClient — wrapper para chamadas à API com retry (máx 60 linhas)

DecisionParser — valida e parseia o JSON de decisão (máx 50 linhas)

ActionRouter — executa a ação decidida (máx 100 linhas)

Orchestrator — compõe as classes acima (máx 80 linhas)

REGRAS:

— Cada classe recebe suas dependências no construtor

— Nenhuma classe acessa os.environ diretamente — recebe config via construtor

— Todos os métodos têm type hints completos

— Erros são específicos: GeminiTimeoutError, InvalidDecisionError, AgentNotFoundError

— O método público é async def process(command: str) → DecisionResult

Implemente as 6 classes com docstrings e type hints. Use dataclasses para configs.

// 08 — PROMPT: STORAGE

Storage e Estado
Centralizado

Refatore o sistema de storage seguindo estes princípios:

1. GCS Client único e limpo:

Crie storage/gcs.py com uma classe GCSClient simples. Métodos: get(path) → Optional[Any], put(path, data), delete(path), list(prefix) → List[str]. Cache interno com TTL como parâmetro. Sem namespace por usuário hardcoded — recebe namespace como argumento do construtor. Todos os métodos têm type hints. Erros lançam StorageError específico.

2. Elimine o VectorStore por enquanto:

FAISS + embeddings do Gemini é poderoso mas desnecessário para o MVP. O knowledge graph + histórico de chat em GCS já provê contexto suficiente. Remova o VectorStore, EpisodicMemory e SharedMemory da fase 1. Documente como feature future.

3. Simplifique o KnowledgeGraph:

Mantenha o grafo mas simplifique: sem chamadas ao Gemini para categorizar conceitos (muito caro). Use um mapa estático simples de categorização. Limite o grafo a 500 nós — se ultrapassar, remova os mais antigos. Salve/carregue do GCS em JSON simples.

4. FinOps simplificado:

Um único JSON no GCS com {date: {tokens, cost, calls}}. Método log_usage(tokens_in, tokens_out). Preços hardcoded com constante nomeada. Sem BigQuery na fase 1. Sem billing API na fase 1.

O resultado deve ser: menos de 400 linhas de código de storage total.

// 09 — PROMPT: CI/CD

Deploy Simplificado
e Confiável

Refatore o CI/CD do GitHub Actions seguindo estas regras:

PROBLEMAS ATUAIS no deploy.yml:

— O Cloud Scheduler é configurado no mesmo job de deploy (falha se já existir e para tudo)

— Não há verificação se o deploy foi bem-sucedido antes de configurar o webhook Telegram

— Secrets são passados como env vars em vez de Secret Manager refs

— Não há smoke test após o deploy

NOVO deploy.yml deve ter os jobs:

job: test — roda pytest, falha o pipeline se teste falhar

job: build (depends: test) — build frontend + imagem Docker

job: deploy (depends: build) — deploy Cloud Run com health check

job: configure (depends: deploy) — configura webhook Telegram e scheduler de forma idempotente

job: notify (depends: deploy) — notifica Telegram com resultado

Cada job tem if: success() exceto notify que tem if: always().

O deploy só completa se GET /health retornar 200 em até 60 segundos. O Telegram webhook é configurado com drop_pending_updates=true e allowed_updates=["message","callback_query"].

O Dockerfile deve usar multi-stage build: stage 1 builda o frontend, stage 2 é Python slim com apenas o necessário.
